# Specification 002: Chroma Vectorization for Efficient Recommendation Retrieval

## Objective

Add a ChromaDB-backed vectorization layer that uses the current Chroma instance running in the Codespace to precompute and index normalized recommendation data, then use that vectorized data to reduce the number of candidate products the TensorFlow.js model must score, while preserving the exact behavior of the current recommendation webpage.

This specification extends Specification 001. The CSV dataset must be used to feed ChromaDB, which will become the canonical source of truth, the browser remains a static single-page application, and the current recommendation webpage functionality must remain exactly the same.

## Critical Constraints

- The live webpage must behave exactly the same as it does today.
- No backend, API, database layer, or server-side recommendation service may be added.
- ChromaDB must be used as a local optimization and indexing layer in the Codespace, not as a runtime UI feature.
- The final recommendation ranking must still be generated by the existing TensorFlow.js model logic, however, now training and predicting based on the vectorized data in ChromaDB.
- If Chroma is empty, it must be fed with the normalized CSV dataset in order to be used as input to the TensorFlow.js model.

## Non-Goals

- Do not redesign the page layout or change any DOM structure.
- Do not modify user-facing text, interaction semantics, or training progress screens.
- Do not replace the existing TensorFlow.js model with Chroma-only retrieval.
- Do not introduce Python-based workflow for model training, indexing, or inference.
- Do not change the app’s static browser-only architecture.

## Design Principles

- Keep the user flow identical: select user, browse products, buy or remove items, train model, and view recommendations.
- Reuse the normalized CSV dataset and existing product/user abstractions created in Specification 001.
- Use Chroma as a vectorized source of truth.
- Preserve the existing output contract for recommendation cards and metadata.
- Treat Chroma as the new source of truth that can be rebuilt without breaking the UI.

## Decisions

- Chroma is used as a local vector index in the Codespace during data preparation and refresh.
- The browser app uses the new dataset service and new model worker that now rely on data from ChromaDB.
- The vectorized data is used for training, predicting, and can be used to narrow the candidate set before the TensorFlow model scores the remaining items.
- Final filtering, ranking, and display remain controlled by the current recommendation logic, but based on the new data source.
- Chroma metadata stores stable IDs and display fields so vector results can be mapped back to the current catalog and user objects.

## Data Layer

### Existing CSV boundary

The application now relies on vectorized data produced from the CSV dataset as the canonical source of truth.

This means the following continue to be true:

1. The browser fetches the data from ChromaDB once through a new ChromaDatasetService.
2. Product rows are aggregated into one catalog product per Product_ID.
3. User rows are grouped by User_ID and stored as strings.
4. Positive Recommended rows remain part of the user interaction history and are not treated as confirmed purchases.
5. The TensorFlow model new trains using the vectorized normalized interaction data.

### Chroma usage model

Chroma is used as a replacement for the CSV dataset, being produced from the CSV dataset if it is still empty.

The implementation should create or reuse collections such as:

- ecommerce_product_vectors
- ecommerce_user_vectors

The vectors must be generated from the same normalized product and user metadata used previously in the app. The vector index must be deterministic and stable so repeated recommendation runs do not produce inconsistent IDs or metadata.

### Product vectorization

Each catalog product should be vectorized from the product metadata available after CSV normalization, including at minimum:

- Product_ID
- category
- brand
- price
- graphSimilarityScore
- federatedClusterId
- localModelAccuracy
- globalModelWeight
- personalizationFactor
- purchaseProbability
- recommendationRate

These fields must be stored with JSON-safe metadata so the browser can map Chroma results back into the existing product object model.

### User vectorization

Each normalized user should be vectorized from the same user summary used in the current UI, including at minimum:

- User_ID
- age
- gender
- location
- device
- timeOfDay
- Session_Duration_Min
- Pages_Viewed
- Previous_Purchases
- User_Rating
- known positive interaction product IDs
- purchased categories and brands

These vectors are used to query the nearest relevant products for the selected user.

### Persistence requirements

- Use the currently running ChromaDB instance in the Codespace as the vector store.
- Persist collection data locally in the configured Chroma storage path.
- Reuse the same stable IDs for products and users across refreshes.
- Keep metadata JSON-serializable and suitable for browser-side matching.
- If the collection is missing, empty, or incompatible, rebuild it from the current normalized CSV dataset without requiring any user-facing indication.

## Application Changes

### Services and startup

Add a lightweight vector service layer to the existing browser app, for example:

- src/service/VectorService.js
- src/service/VectorRetrievalService.js
- src/service/VectorIndexService.js

These services must:

1. Connect to the existing ChromaDB instance in the Codespace.
2. Initialize the collection only once.
3. Reuse an existing collection if it already exists.
4. Rebuild the index from the normalized CSV catalog if the collection is missing or empty.
5. Expose a method that retrieves the most relevant product candidates for a selected user.
6. Return stable product IDs and metadata that align with the current product catalog objects.

These services must be additive. They cannot alter the current page lifecycle, event flow, or the DOM contract.

### Recommendation retrieval flow

The user-visible flow remains the same:

1. User is selected.
2. Products are shown.
3. Training runs.
4. Recommendations appear for the selected user.

Internally, the recommendation request should be adjusted to use vectorized candidate retrieval as a pre-filter before the TensorFlow model is invoked.

Recommended sequence:

1. Build the selected user embedding from the normalized user profile and historical interactions.
2. Query Chroma for the nearest product vectors for that user.
3. Convert Chroma results back into product IDs and metadata.
4. Filter out products the user has already bought or already interacted with in session storage.
5. Pass the narrowed candidate set to the existing TensorFlow recommendation scoring path.
6. Keep the final recommendation rank and score formatting exactly as the current app expects.
7. Return the same recommendation object structure that the page currently renders.

This means the UI remains visually and functionally identical.

### Fallback behavior

If Chroma is unavailable, empty, unreachable, or returns malformed results:

- produce an error log in the console
- stop the app with an error message about the missing vector index

## Implementation Requirements

### Vectorization

1. Use the normalized product catalog and user profiles already produced by the CSV migration.
2. Generate deterministic vectors from the same semantic fields already used by the app.
3. Store vectors in Chroma using stable product IDs and user IDs as keys.
4. Add metadata that can be mapped directly back to existing product/user objects.
5. Keep all vector metadata JSON-serializable and browser-safe.

### Candidate retrieval

1. Query Chroma using the selected user vector.
2. Retrieve the nearest product vectors by similarity.
3. Filter out products already bought or otherwise excluded by the existing logic.
4. Limit the candidate set to a practical size such as 30-100 products before model scoring.
5. Preserve the current model scoring path and product display flow.

### Prediction efficiency

The performance improvement must come from reducing the number of model evaluations per recommendation run.

The final recommendation behavior must remain the same:

- same user-specific recommendations when the user changes,
- same purchase exclusion logic,
- same metadata rendering,
- same descending sort order,
- same recommendation card structure,
- same session-storage behavior.

Chroma should reduce candidate count; it should not change the user-visible result semantics.

## Acceptance Criteria

1. The application requests only the vectorized dataset and does not fetch stale JSON product or user files at runtime.
2. The recommendation webpage continues to show exactly the same user selection, purchase-history, product catalog, and recommendation display behavior.
3. A Chroma collection is created or reused using the current Codespace Chroma database.
4. Product and user vectors are stored with deterministic IDs and metadata that match the normalized dataset.
5. Recommendation requests use Chroma for candidate retrieval before TensorFlow scoring when available.
6. The TensorFlow.js model still reaches 100% progress and emits finite loss and accuracy values.
7. Recommendations remain nonempty, sorted by descending score, and contain stable IDs and display metadata.
8. No fallback path - produce error if can't access ChromaDB.
9. Buying and removing products continues to work without UI change and continues to persist under the existing session-storage schema.
10. Reloading the application still does not reintroduce stale JSON users or products.

## Verification Plan

1. Run the existing data smoke tests to confirm the normalized CSV dataset remains intact.
2. Verify the Chroma collection exists in the current Codespace instance and inspect collection metadata and document counts.
3. Start the app and confirm the same user, product, and purchase-history flows render as before.
4. Select a user with positive interactions and another without positive interactions and verify that the recommendation experience remains unchanged.
5. Train the model from the existing UI and confirm worker completion, progress, and TensorFlow.js logs remain valid.
6. Confirm recommendations remain nonempty and sorted correctly with the same metadata contract.
7. Check that an error is produced if ChromaDB cannot be reached. Try to rebuild Chroma data first.
8. Buy and remove an item, retrain, reload, and verify the same session-storage schema and behavior remain intact.

## Implementation Notes

- This specification is intentionally additive: it introduces vectorized retrieval without changing the external UX contract.
- The vector system is a performance optimization layer, not a feature redesign.
- Reuse the normalized dataset and catalog metadata already created by the CSV migration so no duplicate source-of-truth logic is introduced.
- The local Chroma database already running in the Codespace is the approved integration target.

## Summary

This specification adds a Chroma-backed vector retrieval layer that reduces the candidate space before TensorFlow scoring while preserving the exact behavior of the current recommendation webpage. The HTML, navigation, user flow, product interactions, model training flow, and output formatting remain the same. Chroma acts as a concealed optimization layer that makes recommendation inference more efficient without changing any user-visible functionality.
